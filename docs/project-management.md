# Project Management

## Project management views

- `ProjectListView` loads `GET /v1/projects`, creates projects via `POST /v1/projects`, and opens `ApiKeyRevealDialog` when the create response includes a one-time plaintext `api_key`. Each list row MUST distinguish Cost Level modes: static rows show a `Static` mode tag, the stored `priority_gwei`, and queue-range status; auto rows show an `Auto` mode tag, `auto_queue_position` as a percent, and `auto_max_priority_gwei` as Max.
- `ProjectDetailView` presents a muted LLM API panel (base URL, API key prefix, reset key; rename/delete via overflow menu), a Cost Level panel, a Playground panel, a usage section, and a recent requests section. The Cost Level panel MUST support modes `static` and `auto` with a short explanation for each. Mode and both setting sets MUST persist independently through partial `PUT /v1/projects/:id` after 3 seconds without further changes. Static mode MUST use a logarithmic Gwei slider and numeric input bound to `priority_gwei`, with hard bounds from `GET /v1/llm/billing_config`, plus the existing queue range bar under the slider when live bounds are present. Auto mode MUST use two dual-bar control groups: Queue position (`auto_queue_position` clamped to `[1, 99]` in the WebUI) and Max Cost Level (`auto_max_priority_gwei` with the live Current queue range bar). When a project first enters Auto without a stored cap, the WebUI MUST initialize the cap from current queue max or `min_priority_gwei` and save it with the mode. The panel MUST show two example tables built from `GET /v1/llm/pricing_examples` plus `billing_config`: a Credits table with `Model`, `1M Input`, and `1M Output` columns for separate 1M-token unit prices without `constant_seconds`; and an execution-time table with `Model`, `Input`, `Output`, and `Seconds` for a typical call of `time_prompt_tokens=512` input and `time_completion_tokens=2048` output, including `constant_seconds`, not scaled by Cost Level. Static Credits examples MUST use `priority_gwei` and title `Credits per 1M tokens`. Auto Credits examples MUST use `auto_max_priority_gwei` and title `Maximum Credits per 1M tokens`. Cost-level save feedback uses a single replaceable toast. Rename MUST send only `name`. Below Cost Level, the Playground panel MUST appear as specified in **Playground**. Below Playground, `ProjectUsageSection` MUST show project usage charts from `GET /v1/projects/:id/stats`, `GET /v1/projects/:id/stats/completion-duration`, and `GET /v1/projects/:id/stats/models`. Below Usage, `ProjectRecentRequestsSection` MUST list recent in-progress and finished requests from `GET /v1/projects/:id/requests` with columns Status, Model, VRAM, Input, Output, Duration, Cost Level, Credits, and Time. Status MUST be shown as an icon only: `Clock` for `queued`, `CircleDot` for `in_progress`, `CheckCircle2` for `success`, and `XCircle` for `failed`, with the corresponding status label available to assistive technology. Status icons MUST NOT use animation. In-progress rows MUST show `—` for Input, Output, Duration, and Credits. Failed rows MUST show `—` for Credits. When Input or Output tokens are null, including Image rows, the WebUI MUST show `—`. Duration for finished rows MUST display `Math.round(duration_ms / 1000)` as an integer second count with an `s` suffix. Row keys MUST use `source` and `id`. While any listed row has status `queued` or `in_progress`, the section MUST refresh every 5 seconds; the timer MUST stop when no such rows remain or the component unmounts. The requests list MUST NOT send `limit` or `offset`. Load failures for Usage and Recent Requests MUST use `vue-sonner` toast messages that tell the user to try again later.
- Project data is page state loaded through `projectsAPI`. There is no Pinia project store.
- Plaintext API keys MUST NOT be persisted in local storage or route state after the reveal dialog closes.
- The Project detail API Endpoints panel MUST show the project Base URL before the concrete endpoint in both OpenAI Chat Completions and Responses tabs, with separate copy actions. It MUST show all six Raw Task routes with their HTTP methods, purposes, complete project URLs, parameter placeholders, and independent copy feedback. The Raw Task description MUST state that LLM and Image tasks are supported. The Models tab MUST show separate `GET /models` and `GET /models/image` rows and MUST state that they return only LLM and Image models respectively. Long endpoint URLs MUST wrap without widening the panel.

## Playground

The project detail Playground MUST sit between Cost Level and Usage. It MUST use the same collapsible section pattern as Cost Level. It MUST default to collapsed.

Playground requests MUST call the project's private base URL `/api/<endpoint_token>/v1/...` with the logged-in Crynux AS JWT as `Authorization: Bearer <token>`. The Playground MUST NOT ask the user to paste a project API key and MUST NOT persist a project API key.

The Playground MUST provide two tabs: Chat and Image generation. Each tab MUST include a model picker shared by both tabs. Chat MUST list models from `GET /models`. Image generation MUST list models from `GET /models/image`. When a model list loads successfully and no model is selected, the picker MUST select the first catalog model. Load failures MUST use `vue-sonner` toast messages that tell the user to try again later.

### Local persistence

The Playground MUST persist per-project state in `localStorage` under the key `crynux-as-webui:playground:v1:<projectId>`, where `<projectId>` is the project numeric id. Different projects MUST NOT share Playground state.

Chat persistence MUST include the selected model object and the message list, including each assistant message's `durationSeconds` when present. Image persistence MUST include the selected model object, prompt, negative prompt, steps, the latest generated image as a `data:image/...` URL, elapsed seconds, and whether elapsed time is shown. The Playground MUST NOT persist the chat composer draft, the Thinking checkbox, in-flight flags, or Image error text.

On project detail load, Chat and Image MUST restore persisted state before reconciling the selected model with the catalog. A persisted custom model MUST be kept. A persisted catalog model that still exists in the catalog MUST be kept and refreshed with the catalog `min_vram` and `on_disk_node_count`. A persisted catalog model absent from the catalog MUST fall back to the first catalog model when the list is non-empty. Clearing chat history MUST clear the persisted Chat messages. Image generation success MUST store the PNG as a data URL so refresh restores the image without a `blob:` URL. Storage write failures MUST be logged to the console and MUST NOT block the UI.

### Model picker

The model picker MUST NOT use a Select dropdown. The closed state MUST be a multi-line bordered block that shows the selected model name on the primary line and secondary tags for VRAM (`min_vram` as `<n> GB`) and on-disk node count (`on_disk_node_count` as `<n> nodes`). For Image generation, when `variant` is non-empty, the picker MUST also show a variant tag. An empty Image `variant` MUST NOT render a variant tag.

Clicking the closed block MUST open a Dialog. When the selected model is a catalog model, opening the Dialog MUST leave the search input empty, MUST place the selected catalog row first in the list, and MUST list the remaining catalog models below it. When the selected model is custom, opening the Dialog MUST prefill the search input with that model id and MUST prefill Variant and VRAM from that selection. The Dialog MUST include a search input and a scrollable list of catalog models filtered by case-insensitive substring match on model `id`, and for Image generation also on `variant`. List rows MUST use the same name-plus-tags layout as the closed block. The currently selected catalog model MUST show a selected visual state. Choosing a catalog row MUST update the selection and close the Dialog.

When the search input is non-empty and the filtered catalog list is empty, the Dialog MUST show a custom-model option whose model id is the trimmed search input. Both tabs MUST let the user set VRAM in GB as a positive integer. Image generation MUST also expose a Variant input that MAY be left empty; an empty value MUST be stored and sent as `""`. Confirming a custom model MUST require a Hugging Face model id and a positive integer VRAM, MUST normalize the model id with trim and lowercase, MUST set `on_disk_node_count` to `0`, and MUST close the Dialog. Absolute URLs and any value containing `://` MUST be rejected with an inline error and MUST NOT close the Dialog. Values with whitespace or characters outside the Hugging Face repo-id pattern MUST be rejected the same way. Image custom confirmation MUST NOT require Variant. The Dialog description and search placeholder MUST state that a Hugging Face model id is required and that URLs are not allowed.

When the selected model is custom or its `on_disk_node_count` is `0`, the tab MUST show a fixed hint above the generation UI stating that the model is not yet available on network nodes and that the first request may take much longer while nodes download it. The hint MUST NOT be a toast.

### Chat

Chat MUST present a multi-turn bubble UI: user messages on the right and assistant messages on the left. Each send MUST call the OpenAI-compatible `POST /chat/completions` endpoint with the selected model and the full current message list. When the selected model is custom, the request body MUST include `vram_limit` set to the selected VRAM. Chat MUST keep at most 10 turns (20 messages: 10 user and 10 assistant). Before appending a new user message that would exceed that limit, the WebUI MUST delete the oldest turn. Between the message list and the composer, Chat MUST show a Thinking checkbox. The Thinking checkbox MUST default to checked. Each send MUST include `chat_template_kwargs.enable_thinking` set to the checkbox value. The Thinking checkbox MUST be disabled while a completion request is in flight. The composer MUST be a single-line input. A reload icon button MUST sit as a prefix of that input and share one connected control with it. Clicking the reload button MUST clear the chat history. The reload button MUST be disabled while a completion request is in flight and when the history is empty. The Send action MUST sit as a suffix of that input and share one connected control with it. Pressing Enter in the input MUST send the message. While a completion request is in flight, the input MUST be disabled. While a completion request is in flight, Chat MUST show a Generating bubble with a live elapsed duration in whole seconds to the right of that bubble. When the response arrives, Chat MUST store that turn's final elapsed duration on the assistant message and display it to the right of the assistant bubble. Each assistant message MUST keep its own generation duration across multi-turn chat. A failed request MUST show a toast that tells the user to try again later and MUST NOT leave an empty assistant bubble.

### Image generation

Image generation MUST expose only prompt and negative prompt inputs plus the model picker, a Steps control, and a Generate action. Other Raw Image `task_args` fields MUST use fixed defaults: `num_images=1`, `image_width=512`, `image_height=512`, `cfg=7`, `safety_checker=false`, a generated `seed`, and scheduler `EulerAncestralDiscreteScheduler` with `timestep_spacing=trailing`. Steps MUST be a slider from 1 to 50 with UI default `4`. Generate MUST create a Raw Image task with `task_type=0` through `POST /inference_tasks`, poll `GET /inference_tasks/:id` until `success` or `failed`, then download `GET /inference_tasks/:id/images/0` as PNG bytes, convert the PNG to a data URL, and display that data URL. The create body MUST set `task_args.base_model` to `{ name: <selected id>, variant: <selected variant> }`, where `variant` MAY be an empty string. When the selected model is custom, the create body MUST also include top-level `min_vram` set to the selected VRAM. The image frame MUST always be visible below Generate. When no image is present, the frame MUST show a placeholder message. While a generation request is in flight and no image is present, the frame MUST show Generating image. While a generation request is in flight, Generate MUST show a live elapsed duration in whole seconds to the right of the button. When generation finishes, that duration MUST remain fixed next to the button for both success and failure. Failures MUST show the error text below the Generate button. The displayed error MUST prefer, in order: the create-request API error detail, the polled task `error_message`, a local timeout or other thrown message, then `Image generation failed`. Failures MUST also use `vue-sonner` toast messages. When the displayed error is the generic fallback, the toast MUST tell the user to try again later; otherwise the toast MUST use the same error text shown below the button.

## Static Cost Level control layout

When mode is `static`, the Cost Level controls MUST use this layout:

1. The numeric `priority_gwei` input MUST sit on the left of the control group.
2. The logarithmic slider MUST sit to the right of the numeric input, with `Cheaper` to the left of the slider track and `Faster` to the right of the slider track.
3. The queue range bar MUST sit directly under the slider track when live queue bounds are present.
4. The queue range bar's horizontal track MUST share the same width and the same left/right edges as the slider track (`SliderTrack`). The range bar MUST NOT extend under `Cheaper`, `Faster`, or the numeric input. The range bar MUST sit in the same column as the Slider root and MUST NOT add horizontal padding or inset relative to that column. Thumb overhang MUST NOT change the range bar width.
5. The numeric `priority_gwei` control MUST use a larger type size than the slider side labels and MUST use the primary highlight text color. Its outer bordered box MUST use a tall fixed control height (`h-20`) with flexbox-centered digits around a natural-height input.
6. The digits MUST be vertically centered inside that outer box. The implementation MUST NOT rely on a tall native `<input>` height plus line-height to center the text.
7. The numeric box MUST stay left-aligned in the panel row. The slider-plus-range-bar block MUST occupy about 80% of the remaining row width to the right of the numeric box and MUST be horizontally centered in that remaining space. The slider block MUST be cross-axis centered with the numeric box. The queue range bar MUST size to its visible track and Current queue min / Current queue max labels without extra empty height below the labels.
8. Spacing above the mode cards MUST use `mb-10` after the intro text. Spacing from the mode cards to the control row MUST use `mb-20`. Spacing from the control row to the example tables MUST use `mb-20`.
9. Queue range bar colors and markers MUST follow the Cost Level WebUI rules in Crynux AS `credits-billing.md`: Current queue min and Current queue max labels under the track, blue segment between the mapped queue bounds, red outside that segment.
10. The Cost Level panel intro above the mode cards MUST state that Cost Level controls how many Credits each request spends and how long tasks wait in the queue. That sentence is panel-level intro copy and MUST NOT be placed inside a mode card. Mode cards MUST place Auto on the left and Static on the right. Auto card copy MUST state that the system adjusts Cost Level to the chosen queue position, that Credits for the same task can change, and that Credits never exceed the set maximum. Static card copy MUST state that the same task always spends the same Credits and that tasks may wait too long in the queue. User-facing intro and mode card copy MUST NOT mention Gwei or task fee.
11. When the Cost Level panel is collapsed, the header preview MUST show a mode tag (`Auto` or `Static`) plus the setting values: Auto as `position% · max`, Static as the single `priority_gwei` value.

Any change to the static Cost Level control markup in `ProjectDetailView.vue` MUST be checked against this layout subsection before finishing the change.

## Auto Cost Level control layout

When mode is `auto`, the Cost Level controls MUST follow Crynux AS `credits-billing.md` Auto controls rules and MUST use this layout:

1. Two separate bordered groups MUST appear in order: `Queue position`, then `Max Cost Level`. Vertical spacing between groups MUST be larger than spacing inside one group. The Queue position group description MUST state that when each task is sent, the system reads the current queue min and max Cost Level and sets this request's Cost Level from the configured position.
2. Each group MUST use a left tall numeric input (`h-20`, primary digits, flex-centered) and a right dual-bar block at about 80% of the remaining row width, horizontally centered.
3. Queue position: linear slider with `min=1` and `max=99`; fixed symmetric red–blue–red bar under the slider with blue from 10% to 90% of the track; marker labels `Queue min` and `Queue max`. The slider track MUST be inset so value `1` aligns with `Queue min` and value `99` aligns with `Queue max`. The WebUI MUST clamp stored and edited values into `[1, 99]`.
4. Max Cost Level: logarithmic slider with `Cheaper` / `Faster` labels and the same live Current queue min / Current queue max range bar rules as Static mode.
5. Spacing from the mode cards to the Auto control block and from the Auto control block to the example tables MUST use `mb-20`.

Any change to the auto Cost Level control markup in `ProjectDetailView.vue` MUST be checked against this layout subsection before finishing the change.
