# Project Management

## Project management views

- `ProjectListView` loads `GET /v1/projects`, opens `CreateProjectDialog` automatically when the loaded project list is empty, creates projects via `POST /v1/projects`, opens `ApiKeyRevealDialog` for the one-time plaintext `api_key` returned by create, and navigates to `ProjectDetailView` for the new project after `ApiKeyRevealDialog` closes. Above the project list, `AccountUsageStats` MUST load `GET /v1/account/stats` and show six summary cards: Requests, Input tokens, Output tokens, Images (`image_count`), Credits used, and Success rate, plus Requests and Credits used charts for the selected range. Each list row MUST distinguish Cost Level modes with a mode tag and one metric pair: Auto shows `Queue position` with `auto_queue_position` as a percent and `Max Credits`; Static shows `Cost Level` as a plain integer from `priority_gwei` with no unit label and `Max Credits`. Each metric MUST place the number above its title, separated by a vertical divider, matching the Requests today Success/Failed layout. The list MUST load Crynux queue bounds, Provider queue bounds, and Provider min Credits hints from `GET /v1/llm/billing_config`. Hint text MUST follow Crynux AS `credits-billing.md` project-list rules: Auto shows only Provider availability; Static shows Open source queue status, Provider queue status only when Provider models are enabled, and Provider availability reasons that distinguish Cost Level limits from Max Credits limits. Each hint line MUST use its own color.
- `ProjectDetailView` presents a muted LLM API panel (base URL, API key prefix, reset key; rename/delete via overflow menu), a Cost Level panel, a Playground panel, a usage section, and a recent requests section. The Cost Level panel MUST support modes `static` and `auto` with a short explanation for each. Mode and both setting sets MUST persist independently through partial `PUT /v1/projects/:id` after 3 seconds without further changes. Static mode MUST use a logarithmic slider and plain integer numeric input bound to `priority_gwei`, where `1` displayed Cost Level equals `1000` Gwei, with Static hard bounds from `GET /v1/llm/billing_config`, plus separate Crynux and Provider queue range bars under the slider, a Provider admission marker for `provider_min_priority_gwei`, and a Provider availability explanation for the current Cost Level. The numeric input, collapsed Static preview, project list, Credits usage, and Recent Requests MUST show Cost Level as a plain number and MUST NOT show `kgwei`, `gwei`, or any other unit label. Slider and input edits MUST quantize to that integer display unit and MUST submit `priority_gwei` as the corresponding Gwei decimal string. Credits example math MUST keep using Gwei values. Below the Task queue panel, Static MUST show the same Max Credits per task group as Auto (`auto_max_credits_per_task` positive integer input plus logarithmic Credits slider with a Provider min bar). Auto mode MUST use Queue position (`auto_queue_position` clamped to `[1, 99]` in the WebUI) and Max Credits per task. When a project first enters Auto or Static without a stored Max Credits value, the WebUI MUST initialize it from `default_auto_max_credits_per_task` and save it with the mode. `provider_min_priority_gwei`, `provider_min_credits_cheapest`, and `provider_min_credits_expensive` MUST be treated as UI reference hints for the fixed request size returned by `provider_min_reference_input_tokens` and `provider_min_reference_output_tokens` (`10` input and `50` output). The Cost Level Provider min marker MUST keep the under-label `Provider min`. The Max Credits bar MUST show separate `Provider min - cheapest` and `Provider min - expensive` markers. Tooltips and availability copy MUST say that actual Provider admission depends on the selected model and request size. Max Credits availability MUST distinguish covering only cheapest models from covering all Provider models. Static MUST NOT auto-adjust Cost Level when Max Credits is exceeded; the backend rejects those requests. Below the Cost Level controls, the panel MUST show Chat and Image tabs, each with two example tables. Chat MUST use `GET /v1/llm/pricing_examples` plus `billing_config`: a Credits table with `Model`, `1M Input`, and `1M Output` columns for separate 1M-token unit prices without `constant_seconds`; and an execution-time table with `Model`, `Input`, `Output`, and `Seconds` for a typical call of `time_prompt_tokens=512` input and `time_completion_tokens=2048` output, including `constant_seconds`, not scaled by Cost Level. Static Chat Credits examples MUST use `priority_gwei` and title `Credits per 1M tokens`. Auto Chat Credits examples MUST use the current Crynux queue high when available otherwise the median, with title `Credits per 1M tokens`. Image MUST use `GET /v1/llm/image_pricing_examples` plus `billing_config` for a fixed workload of `example_width×example_height` (`512×512`), `example_steps` (`20`), and `example_num_images` (`1`): a Credits table with `Model`, `Size`, `Steps`, and `Credits` (including `overhead_seconds`); and an execution-time table with `Model`, `Size`, `Steps`, and `Seconds` (including `overhead_seconds`, not scaled by Cost Level). When an Image example row's `components` include repository names, the Model cell MUST show those repos as muted small text on a new line under the model id. Static and Auto Image Credits titles MUST be `Credits per image`. When a Credits example cell truncates to `0`, the WebUI MUST display `<1` instead of `0`. Cost-level save feedback uses a single replaceable toast. Rename MUST send only `name`. Below Cost Level, the Playground panel MUST appear as specified in **Playground**. Below Playground, `ProjectUsageSection` MUST show project usage charts from `GET /v1/projects/:id/stats`, `GET /v1/projects/:id/stats/completion-duration`, and `GET /v1/projects/:id/stats/models`. The Tokens & Images chart MUST plot Input and Output tokens on the left Y-axis and Images (`token_series.image_count`) on the right Y-axis, with outer axis titles `Tokens` and `Images`, a legend that labels Input, Output, and Images, and distinct series colors. Top Models rows MUST use the Relay loaded-model identity `(model_cache_hash, execution_dtype)` returned by the stats API and MUST NOT merge rows that differ only by display model id. The Model cell MUST show `model` plus quantization and replaced-component repos using the same summary layout as Cost Level / Playground. The Usage column MUST replace separate Input and Output columns: Chat rows MUST show compact input and output token counts; Image rows MUST show only the aggregated `image_count` with muted `images` label, not Size or Steps. Below Usage, `ProjectRecentRequestsSection` MUST list recent in-progress and finished requests from `GET /v1/projects/:id/requests` with columns Status, Model, VRAM, Usage, Duration, Cost Level, Credits, and Time. Cost Level cells MUST show a plain integer with no unit label, rounding half-up from the returned Gwei value. The Model cell MUST show quantization and component repos when the API returns them. The Usage column MUST show Chat input/output tokens as two compact lines, or Image `W×H` and `N steps` (with `×M` when `image_count > 1`). Status MUST be shown as an icon only: `Clock` for `queued`, `CircleDot` for `in_progress`, `CheckCircle2` for `success`, and `XCircle` for `failed`, with the corresponding status label available to assistive technology. Status icons MUST NOT use animation. Below the Model cell, in-progress and queued rows MUST show a muted secondary line with a small phase icon and one short user-facing sentence for the request `phase`. The sentence MUST NOT expose Bridge or Relay internal names, VSS, or validation-group details. Failed rows MUST show a muted secondary line with an alert icon and one short sentence when `error_message` is present: known Bridge snake_case codes MUST map to short user-facing text without protocol jargon, and unknown values MUST display as returned. Failed rows without `error_message` and successful rows MUST omit the secondary line. Long secondary-line text MUST truncate with the full string in `title`. In-progress rows MUST show `—` for Usage, Duration, and Credits. Failed rows MUST show `—` for Credits. When Usage fields are null or missing, the WebUI MUST show `—`. Duration for finished rows MUST display `Math.round(duration_ms / 1000)` as an integer second count with an `s` suffix. Row keys MUST use `source` and `id`. The section MUST load once on mount and again when `projectId` changes. It MUST NOT poll or auto-refresh on a timer. The requests list MUST NOT send `limit` or `offset`. Load failures for Usage and Recent Requests MUST use `vue-sonner` toast messages that tell the user to try again later.
- Project data is page state loaded through `projectsAPI`. There is no Pinia project store.
- Plaintext API keys MUST NOT be persisted in local storage or route state after the reveal dialog closes.
- The Project detail API Endpoints panel MUST NOT repeat the project Base URL inside the OpenAI Chat Completions, Responses, or Images tabs. Those tabs MUST show only the concrete endpoint URL(s) with copy actions. The OpenAI Images tab MUST show `POST /images/generations` and `POST /images/edits` as two separate endpoint rows. It MUST show all eight Raw Task routes with their HTTP methods, purposes, complete project URLs, parameter placeholders, and independent copy feedback, including `POST /inference_tasks/:client_task_id/abort` and `POST /inference_tasks/batch/abort`. The Raw Task description MUST state that LLM and Image tasks are supported. The Models tab MUST show separate `GET /models` and `GET /models/image` rows and MUST state that they return only LLM and Image models respectively. Long endpoint URLs MUST wrap without widening the panel.

## Playground

The project detail Playground MUST sit between Cost Level and Usage. It MUST use the same collapsible section pattern as Cost Level. It MUST default to collapsed. Within an open Playground, Chat and Image tab panels MUST remain mounted while switching tabs (`unmount-on-hide` false) so an in-flight request on one tab continues without remounting.

Playground requests MUST call the project's private base URL `/api/<endpoint_token>/v1/...` with the logged-in Crynux AS JWT as `Authorization: Bearer <token>`. The Playground MUST NOT ask the user to paste a project API key and MUST NOT persist a project API key.

The Playground MUST provide two tabs: Chat and Image generation. Each tab MUST include a model picker shared by both tabs. Chat MUST list models from `GET /models`. Image generation MUST list models from `GET /models/image`. When a model list loads successfully and no model is selected, the picker MUST select the first catalog model. Load failures MUST use `vue-sonner` toast messages that tell the user to try again later.

### Local persistence

The Playground MUST persist per-project state in `localStorage` under the key `crynux-as-webui:playground:v1:<projectId>`, where `<projectId>` is the project numeric id. Different projects MUST NOT share Playground state.

Chat persistence MUST include the selected model object, the message list, including each assistant message's `durationSeconds` when present, the latest task status log, and when a create has returned an id that is still unfinished, `inFlightTaskId` plus `inFlightStartedAt` (Unix milliseconds). Image persistence MUST include the selected model object, prompt, negative prompt, steps, the latest generated image as a `data:image/...` URL, elapsed seconds, whether elapsed time is shown, the latest task status log, and the same in-flight fields when applicable. Each status log entry MUST store an ISO-8601 `at` timestamp, `phase`, optional `estimatedCompletionAt`, and optional `message`. `phase` MAY be the local WebUI value `sending`, or a task `phase` returned by AS. The Playground MUST NOT persist the chat composer draft, the Thinking checkbox, or Image error text.

After `POST /inference_tasks` returns a task id, Chat and Image MUST write that id to the corresponding in-flight fields immediately and MUST clear those fields when the task reaches `success` or `failed`, when Chat history is cleared, or when a new send/generate replaces the previous in-flight task. On Chat or Image mount (including after page refresh, collapsing then reopening Playground, or navigating away and back to the project), when `inFlightTaskId` is present the tab MUST resume polling that task, restore the Generating UI, continue the status log from polled phases, and fetch the result on success. Elapsed time MUST continue from `inFlightStartedAt` when present. A create that has not yet returned an id MUST NOT be resumable after unmount. An orphaned in-flight poll from a previous component instance MUST NOT update UI or clear another instance's persisted in-flight id.

On project detail load, Chat and Image MUST restore persisted state before reconciling the selected model with the catalog. A persisted custom model MUST be kept. A persisted Image catalog model MUST carry `model_cache_hash`; a persisted Image catalog selection without `model_cache_hash` MUST be discarded and MUST NOT be matched to a catalog row by `id`, `quantization_config`, `execution_dtype`, or any other fuzzy rule. A persisted catalog model that still exists in the catalog under the same selection key MUST be kept and refreshed with the catalog `min_vram`, `on_disk_node_count`, `quantization_config`, `execution_dtype`, `model_cache_hash`, `components`, and `lora`. The selection key of an Image catalog model is its `model_cache_hash`. The selection key of a Chat catalog model is `(id, quantization_config, execution_dtype)`. The selection key of a custom model is `(id, quantization_config, execution_dtype)` in a key namespace distinct from catalog keys. A persisted catalog model absent from the catalog MUST fall back to the first catalog model when the list is non-empty. Clearing chat history MUST clear the persisted Chat messages and Chat in-flight fields. Image generation success MUST store the PNG as a data URL so refresh restores the image without a `blob:` URL. Storage write failures MUST be logged to the console and MUST NOT block the UI.

### Model picker

The model picker MUST NOT use a Select dropdown. The closed state (the selected-model block in the Chat and Image Playground tabs) and each Dialog catalog row MUST share one summary layout.

The summary MUST place the model `id` on the primary line at the left. On the same line at the right, the summary MUST show two numeric cells with the value above a muted caption: VRAM as `><n>GB` when `min_vram` is greater than zero (caption `VRAM`), and on-disk node count as the integer `on_disk_node_count` (caption `nodes`).

Below that line, the summary MUST show a detail row with a Quantization column and, when present, a Components column.

The Quantization column MUST always render. When `quantization_config` is present, its value MUST be `<quant_method>-<bitwidth>` when both are available (for example `bitsandbytes-4bit`), otherwise the available method or bit width alone. When there is no quantization, or neither method nor bit width can be determined, the value MUST be `full`. The Quantization column MUST NOT show `llm_int8_threshold` or `execution_dtype`, and MUST NOT list component names.

The Components column MUST render only replaced pipeline components from the `components` object. Each entry MUST show only `components[<name>].repo` on one line. Entries without a non-empty `repo` MUST be omitted. The Components column MUST NOT show the component usage name, MUST NOT invent rows from `quantization_config.components_to_quantize`, MUST NOT fall back to the base model `id` as a component repo, and MUST NOT use hardcoded component display names. When a replaced component name also appears in `quantization_config.components_to_quantize`, the repo line MUST append `-<bitwidth>` (for example `org/te-override-4bit`) using the bit width of that row's `quantization_config`. `components_to_quantize` selects task-time quantization targets and MUST NOT be treated as the replacement list.

When Components has no content, the Quantization column MUST occupy the full detail-row width. The picker MUST NOT show an Image `variant` field or any Variant input.

Clicking the closed block MUST open a Dialog. When the selected model is a catalog model, opening the Dialog MUST leave the search input empty, MUST place the selected catalog row first in the list, and MUST list the remaining catalog models below it. When the selected model is custom, opening the Dialog MUST prefill the search input with that model id and MUST prefill VRAM from that selection. The Dialog MUST include a search input and a scrollable list of catalog models filtered by case-insensitive substring match on model `id`, quantization label, replaced-component usage names and repos, and `execution_dtype`. List rows MUST use the same summary layout as the closed block. The currently selected catalog model MUST show a selected visual state. Choosing a catalog row MUST update the selection to the full selected config (`id`, `min_vram`, `on_disk_node_count`, `execution_dtype`, `quantization_config`, `model_cache_hash`, `components`, `lora`) and close the Dialog. The Image picker identifies the selected row by `model_cache_hash`.

When the search input is non-empty and the filtered catalog list is empty, the Dialog MUST show a custom-model option whose model id is the trimmed search input. Both tabs MUST let the user set VRAM in GB as a positive integer. Confirming a custom model MUST require a Hugging Face model id and a positive integer VRAM, MUST normalize the model id with trim and lowercase, MUST set `on_disk_node_count` to `0`, MUST set `quantization_config` to `null` and `execution_dtype` to an empty string, and MUST close the Dialog. Absolute URLs and any value containing `://` MUST be rejected with an inline error and MUST NOT close the Dialog. Values with whitespace or characters outside the Hugging Face repo-id pattern MUST be rejected the same way. The Dialog description and search placeholder MUST state that a Hugging Face model id is required and that URLs are not allowed.

When the selected model is custom or its `on_disk_node_count` is `0`, the tab MUST show a fixed hint above the generation UI stating that the model is not yet available on network nodes and that the first request may take much longer while nodes download it. The hint MUST NOT be a toast.

### Chat

Chat MUST present a multi-turn bubble UI: user messages on the right and assistant messages on the left. Each send MUST create a Raw LLM task with `task_type=1` through `POST /inference_tasks`, poll `GET /inference_tasks/:id` until `success` or `failed`, then download `GET /inference_tasks/:id/llm` and append the assistant text from the raw result. The create body MUST set `task_args` to a canonical GPT task JSON string for the selected model and the full current message list, with `version` `3.7.0`, `template_args.enable_thinking` set from the Thinking checkbox, `generation_config.max_new_tokens` `2048`, and `quantization_config` set to the selected catalog value or `null`. When the selected catalog row has a non-empty `execution_dtype`, `task_args.dtype` MUST be set to that value. When the selected model is custom, the create body MUST also include top-level `min_vram` set to the selected VRAM. Chat MUST keep at most 10 turns (20 messages: 10 user and 10 assistant). Before appending a new user message that would exceed that limit, the WebUI MUST delete the oldest turn. Between the message list and the composer, Chat MUST show a Thinking checkbox. The Thinking checkbox MUST default to checked. The Thinking checkbox MUST be disabled while a request is in flight. The composer MUST be a single-line input. A reload icon button MUST sit as a prefix of that input and share one connected control with it. Clicking the reload button MUST clear the chat history and the Chat status log. The reload button MUST be disabled while a request is in flight and when the history is empty. The Send action MUST sit as a suffix of that input and share one connected control with it. Pressing Enter in the input MUST send the message. While a request is in flight, the input MUST be disabled. While a request is in flight, Chat MUST show a Generating bubble with a live elapsed duration in whole seconds to the right of that bubble. When the response arrives, Chat MUST store that turn's final elapsed duration on the assistant message and display it to the right of the assistant bubble. Each assistant message MUST keep its own generation duration across multi-turn chat. A failed request MUST show a toast that tells the user to try again later and MUST NOT leave an empty assistant bubble.

Below the Send control, Chat MUST show a status log. Each new Send MUST clear that log before recording new entries. Immediately before `POST /inference_tasks`, Chat MUST append one local log line with phase `sending`. That line covers the create request round-trip while AS validates `task_args`, checks the model, and estimates the task fee; the task does not exist as `queued` until create returns. After create returns and while polling, Chat MUST append one log line when the task `phase` changes. Each line MUST show a small phase icon, the local browser timestamp, and one plain-language sentence for the phase that states where the task is and what is happening. When `phase` is `running` and `estimated_completion_at` is present, the line MUST also show that estimated completion time formatted in the browser local timezone. When `phase` is `failed` and `error_message` is present, the line MUST use the failure explanation sentence for that code instead of the short phase label. The latest Chat status log MUST persist in `localStorage` and MUST restore after refresh.

### Image generation

Image generation MUST expose only prompt and negative prompt inputs plus the model picker, a Steps control, and a Generate action. Other Raw Image `task_args` fields MUST use fixed defaults: `version` `3.7.0`, `num_images_per_prompt=1`, `image_width=512`, `image_height=512`, `guidance_scale=7`, and a generated `seed`. Steps MUST be a slider from 1 to 50 with UI default `4`. Generate MUST create a Raw Image task with `task_type=0` through `POST /inference_tasks`, poll `GET /inference_tasks/:id` until `success` or `failed`, then download `GET /inference_tasks/:id/images/0` as PNG bytes, convert the PNG to a data URL, and display that data URL. The create body MUST set `task_args.base_model` to `{ name: <selected id> }` with no `variant` field. When the selected catalog row has a non-empty `execution_dtype`, `task_args.dtype` MUST be set to that value. When the selected catalog row has a non-null `quantization_config`, `task_args.quantization_config` MUST be set to that object. When the selected catalog row has non-null `components`, `task_args.components` MUST be set to that object. When the selected catalog row has non-null `lora`, `task_args.lora` MUST be set to that value. The submitted `task_args` MUST match the configuration displayed in the picker. When the selected model is custom, the create body MUST also include top-level `min_vram` set to the selected VRAM. The image frame MUST always be visible below Generate. When no image is present, the frame MUST show a placeholder message. While a generation request is in flight and no image is present, the frame MUST show Generating image. While a generation request is in flight, Generate MUST show a live elapsed duration in whole seconds to the right of the button. When generation finishes, that duration MUST remain fixed next to the button for both success and failure. Failures MUST show the error text below the Generate button. The displayed error MUST prefer, in order: the create-request API error detail, the polled task `error_message`, a local timeout or other thrown message, then `Image generation failed`. Failures MUST also use `vue-sonner` toast messages. When the displayed error is the generic fallback, the toast MUST tell the user to try again later; otherwise the toast MUST use the same error text shown below the button.

Below the Generate control, Image MUST show a status log with the same phase-change rules as Chat, including the local `sending` line before create returns. Each new Generate MUST clear that log before recording new entries. The latest Image status log MUST persist in `localStorage` and MUST restore after refresh.

## Static Cost Level control layout

When mode is `static`, the Cost Level controls MUST use this layout:

1. The plain integer Cost Level input MUST sit on the left of the top control row, directly beside the slider, so the input and slider read as one control. The input MUST NOT show a unit label.
2. The logarithmic slider MUST sit to the right of the numeric input, with `Cheaper` between the input and the slider track and `Faster` to the right of the slider track. Slider output MUST quantize to the integer Cost Level display unit while keeping the existing natural-log axis.
3. Under that top row, a bordered muted Task queue panel MUST span the full content width of the Cost Level card with equal left and right panel edges. Standard horizontal padding applies to the panel title and footer hint. The queue bars and their row labels MUST share the top row's right inset so bar edges stay aligned with the slider track while the panel background itself does not shrink. The panel MUST use the same bordered muted group style as Auto Cost Level groups. Inside the panel, `Task queue` MUST be a section title above two rows: `Open source models` and `Provider models`. Each queue title MUST sit in the label column under `Cheaper`; each range bar MUST occupy the slider column. Each queue range bar MUST always render a thicker full-width track. When a queue is empty, that bar MUST keep the track, MUST NOT draw red/blue queue segments or min/max markers, and MUST show `Queue empty` centered inside the track. Vertical spacing between the two queue rows MUST be larger than the gap between the slider row and the Task queue panel. Queue min and queue max labels MUST sit above the track, with the min label entirely to the left of its tick and the max label entirely to the right of its tick. The Provider admission marker MUST be drawn on the Provider models bar at the shared `provider_min_priority_gwei` tick with under-label `Provider min`, and the track segment to the left of that marker MUST always be red. Below the queue bars, the panel MUST show one small explanatory line for the current setting against that reference, including both cheapest and expensive Credits amounts.
4. The top input-and-slider row MUST stay outside the Task queue panel. That row and the Task queue rows MUST share one column grid so each range bar's left and right edges align with the slider track (`SliderTrack`) left and right edges. Bars MUST NOT extend under `Cheaper`, `Faster`, the queue titles, or the numeric Cost Level input.
5. The numeric Cost Level control MUST use a larger type size than the slider side labels and MUST use the primary highlight text color. Its outer bordered box MUST use a tall fixed control height (`h-20`) with flexbox-centered digits around a natural-height input and MUST NOT show a unit label.
6. The digits MUST be vertically centered inside that outer box. The implementation MUST NOT rely on a tall native `<input>` height plus line-height to center the text.
7. The top control row and the Task queue panel MUST use the full content width of the Cost Level card. The previous 80%-width centered slider block MUST NOT be used.
8. Spacing above the mode cards MUST use `mb-10` after the intro text. Spacing from the mode cards to the control block MUST use `mb-20`. Spacing from the control block to the example tables MUST use `mb-20`.
9. Queue range bar colors and markers MUST follow the Cost Level WebUI rules in Crynux AS `credits-billing.md`.
10. The Cost Level panel intro above the mode cards MUST state that Cost Level controls how many Credits each request spends and how long tasks wait in the queue. Mode cards MUST place Auto on the left and Static on the right. Auto card copy MUST state that the system adjusts Cost Level toward the chosen queue position within Max Credits per task. Static card copy MUST state that the same task always spends the same Credits and that tasks may wait too long in the queue. User-facing Cost Level copy, numeric controls, and previews MUST NOT mention Gwei, kgwei, task fee, or any other unit label.
11. Below the Task queue panel, Static MUST show the Max Credits per task group with the same input, logarithmic Credits slider, Provider min bar, and Max Credits Provider availability explanation as Auto. Vertical spacing between the Cost Level / Task queue block and Max Credits MUST match Auto group spacing (`space-y-10`). The Static Max Credits description MUST state that estimated Credits above the budget are rejected without changing Cost Level.
12. When the Cost Level panel is collapsed, the header preview MUST show a mode tag (`Auto` or `Static`) plus one right-aligned metric pair with numbers above titles: Auto MUST show `Queue position` and `Max Credits`; Static MUST show `Cost Level` and `Max Credits`. The preview MUST NOT join those values with `/` or `·`, MUST NOT use a flat key-value row layout, and MUST NOT show a unit label on Cost Level.

Any change to the static Cost Level control markup in `ProjectDetailView.vue` MUST be checked against this layout subsection before finishing the change.

## Auto Cost Level control layout

When mode is `auto`, the Cost Level controls MUST follow Crynux AS `credits-billing.md` Auto controls rules and MUST use this layout:

1. Two separate bordered groups MUST appear in order: `Queue position`, then `Max Credits per task`. Vertical spacing between groups MUST be larger than spacing inside one group.
2. Queue position MUST keep the left tall numeric input and right dual-bar block: linear slider with `min=1` and `max=99`; fixed symmetric red–blue–red bar under the slider with blue from 10% to 90% of the track; marker labels `Queue min` and `Queue max` above the bar, with min entirely left of its tick and max entirely right of its tick.
3. Max Credits per task MUST use a left tall positive integer input and a right logarithmic Credits slider. The slider visible axis MUST pack the current Max Credits value, `provider_min_credits_cheapest`, and `provider_min_credits_expensive` with margin, with hard bounds `[1, 10000]`. Side labels MUST be `Lower` and `Higher`. Under the slider track, a range bar MUST show two Provider min markers for `provider_min_credits_cheapest` and `provider_min_credits_expensive`, with under-labels `Provider min - cheapest` and `Provider min - expensive`, and a red segment to the left of the cheaper marker. Below the slider and Provider min bar, the group MUST show availability for that reference in three states: all Provider models covered, only cheapest Provider models covered, or no Provider models covered.
4. Spacing from the mode cards to the Auto control block and from the Auto control block to the example tables MUST use `mb-20`.

Any change to the auto Cost Level control markup in `ProjectDetailView.vue` MUST be checked against this layout subsection before finishing the change.
